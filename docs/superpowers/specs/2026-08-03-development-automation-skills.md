## Context

The PH `development` skill orchestrates three phases: content writing (writer.md), content review (editor.md), and automation (automation.md). The automation phase currently wraps `agnosticv:catalog-builder` for catalog creation and references automation guides inline. This spec introduces two new standalone skills to handle the actual automation code authoring — one per automation approach.

---

## Architecture

`automation.md` reads `publishing-house/spec/automation-manifest.yaml` to determine the automation approach, then dispatches to the appropriate skill. Both skills are self-contained and can also be invoked standalone.

```
development skill
  └── automation.md
        reads: publishing-house/spec/automation-manifest.yaml
        dispatches based on manifest.automation_approach:
          "ansible"  → Skill tool: rhdp-publishing-house:ansible-helper  (Mitesh, RHDPCD-110)
          "gitops"   → Skill tool: rhdp-publishing-house:gitops-helper   (Juliano, RHDPCD-111)
          "both"     → calls both sequentially (ansible first, then gitops)
```

The automation manifest (`publishing-house/spec/automation-manifest.yaml`) is generated by automation.md Phase 7a — it captures what pre-configuration the environment needs. Skills read this manifest to understand what to build.

## Model Policy

No `model:` field in any SKILL.md or agent frontmatter. All skills and agents inherit the model from the user's Claude Code session. See the [consolidation architecture spec](2026-06-29-ph-skills-consolidation-architecture.md) for rationale.

## Standard PH SKILL.md Skeleton

Both skills MUST follow the same skeleton used by intake, development, and all other PH skills. This ensures pre-flight auth, workflow stage gating, and tool boundaries are consistent across the repo.

All metadata goes in a single frontmatter block:

```yaml
---
name: rhdp-publishing-house:<skill-name>
description: This skill should be used when the user asks to "..."
context: main
---
```

No `model:` field — skills inherit from the user's session.

## Skill 1: gitops-helper (Juliano — RHDPCD-111)

### Responsibility

Writes GitOps automation for RHDP lab environments — Helm charts, ArgoCD applications, and supporting manifests that provision the lab environment pre-student.

### Directory structure

```
rhdp-publishing-house-skills/
└── skills/
    └── gitops-helper/
        ├── SKILL.md
        └── references/
            └── gitops-patterns.md    ← Helm/ArgoCD conventions for RHDP
```

### SKILL.md frontmatter

```yaml
---
name: rhdp-publishing-house:gitops-helper
description: This skill should be used when the user asks to "write GitOps automation", "create Helm charts", "set up ArgoCD for this lab", or "build GitOps deployment". Handles GitOps (Helm + ArgoCD) automation authoring for RHDP lab environments.
context: main
---
```

### Step 5 — Read project context (gitops-specific)

Reads from the author's project repo:
- `publishing-house/spec/automation-manifest.yaml` — what needs to be pre-provisioned
- `publishing-house/spec.yaml` — environment details (ocp_version, topology, cloud_provider)
- `publishing-house/spec/design.md` — products and technologies to understand what to deploy

### Output

Writes to the author's project repo:
- `automation/helm/` — Helm chart(s) for environment components
- `automation/argocd/` — ArgoCD Application manifests
- `automation/README.md` — deployment instructions

### Scope (what Juliano owns)

- Helm chart structure and values patterns for RHDP lab components
- ArgoCD Application manifest generation
- Reference to RHDP GitOps golden repo patterns (Juliano's domain expertise)
- `references/gitops-patterns.md` — Juliano writes and maintains this reference file

### Out of scope

- AgnosticV catalog creation — that's `agnosticv:catalog-builder` called by automation.md Phase 7b
- Ansible playbooks — that's ansible-helper (Mitesh)
- Infrastructure sizing decisions — those come from spec.yaml

## Contribution Pattern

Both Juliano and Mitesh follow the same contribution process.

### Repo and branch

- **Target repo:** `rhdp-publishing-house-skills` (NOT a new repo)
- **Branch naming:** `RHDPCD-111-gitops-helper` (Juliano), `RHDPCD-110-ansible-helper` (Mitesh)

### What to create

**Juliano:**
```
skills/gitops-helper/
  ├── SKILL.md              ← single frontmatter block, no model: field
  └── references/
      └── gitops-patterns.md
```

**Mitesh:**
```
skills/ansible-helper/
  ├── SKILL.md              ← single frontmatter block, no model: field
  └── references/
      └── ansible-patterns.md
```

### PR process

1. Branch from `main`
2. Create `SKILL.md` following the standard skeleton (single frontmatter block, pre-flight, workflow check, tool boundaries)
3. Create `references/` directory with domain-specific patterns file
4. PR title: `[RHDPCD-111] Add rhdp-publishing-house:gitops-helper` (or RHDPCD-110 for Mitesh)
5. Reviewer: Prakhar Srivastava
6. After merge: Prakhar updates `skills/development/procedures/automation.md` to wire the dispatch

### What each person does NOT need to do

- Do NOT update `automation.md` — Prakhar wires the dispatch after each skill merges
- Do NOT update `plugin.json` — no version bump needed for adding skills within the existing plugin
- Do NOT create a new plugin or repo — these go into the existing `rhdp-publishing-house` plugin
- Do NOT skip pre-flight or workflow check — every PH skill must verify project auth and stage
- Do NOT add a `model:` field — skills inherit from the user's session
- Do NOT use double frontmatter blocks — all metadata in one `---` block

## automation.md Dispatch (Prakhar updates after each skill merges)

After each skill is merged, Prakhar updates `skills/development/procedures/automation.md` Phase 7c to dispatch:

```
## Phase 7c: Automation Code

Read `publishing-house/spec/automation-manifest.yaml` → check `automation_approach` field.

- `automation_approach: ansible`  → invoke `rhdp-publishing-house:ansible-helper`
- `automation_approach: gitops`   → invoke `rhdp-publishing-house:gitops-helper`
- `automation_approach: both`     → invoke ansible-helper first, then gitops-helper
- `automation_approach: none`     → skip 7c, proceed to 7d

Pass the automation manifest path and spec.yaml path to the invoked skill.
```
